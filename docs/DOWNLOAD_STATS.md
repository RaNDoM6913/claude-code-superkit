# Память счётчиков Superkit

Этот файл — инструкция для следующих просьб «обнови скачивания и установки»,
«обнови пиллы», «обнови статистику». Источник сохранённых чисел —
[дневной реестр](metrics/downloads-state.json). Сначала прочитать оба файла,
затем получать новые данные. Не начинать историю заново.

## Что выбрал владелец

В шапке README два отдельных пилла: **NPM DOWNLOADS** и **GIT CLONES**.
В самих пиллах нет `TOTAL`, `14D` и уникальных клонеров. Даты, ограничения
и происхождение чисел находятся в раскрываемом `About these counters`.
Каналы не складываются. Скачивания архивов релизов сохраняются отдельно,
но не входят в эти два пилла.

Фраза «скачивания и установки» означает обновление этих доступных метрик,
а не разрешение считать скачивания установками или внедрять телеметрию.
Успешные установки сейчас **не измеряются**, значение — `null`, а не ноль.

## Как обновлять по следующей просьбе

1. Прочитать реестр и проверить суммы сохранённых дней. Уточнить его актуальный
   `data_through` для каждого источника; не использовать дату этого документа
   как границу данных. Сохранить старые итоги для отчёта о разнице.
2. Для npm запросить
   `https://api.npmjs.org/downloads/point/last-day/claude-code-superkit`,
   чтобы определить последний доступный день. Получить дневные значения через
   `https://api.npmjs.org/downloads/range/START:END/claude-code-superkit`:
   взять сохранённый последний день и до семи предыдущих дней для сверки,
   затем все новые доступные дни. При большом интервале разбить запросы на
   поддерживаемые API диапазоны. Не заменять исторический итог значением
   `last-month` и не прибавлять месячный итог к сохранённому числу.
3. Для Git выполнить чтение
   `gh api repos/RaNDoM6913/claude-code-superkit/traffic/clones`.
   Использовать `clones[].timestamp` и `clones[].count`, а не прибавлять
   верхнеуровневый `count` из очередного скользящего окна. Сохранить также
   границы и агрегаты последнего ответа в `last_api_window`.
4. Объединять по ключу **UTC-дата**. Новая дата добавляется один раз.
   Если дата уже сохранена, сверить значение; при корректировке источника
   заменить прежнее число и отдельно отметить исправление в журнале.
   Повторное получение тех же данных не меняет итог. Старые дни, которые уже
   не возвращаются API, остаются в реестре.
5. Пересчитать итог как сумму всех сохранённых дневных значений. Пропущенный
   день не означает ноль. Проверить непрерывность от `coverage_start` до
   `data_through`. Не добавлять сегодняшний день, пока он не завершился по UTC;
   при необходимости сохранить его только как явно предварительное наблюдение
   отдельно от счётчика. Не дописывать отсутствующие в ответе даты нулями.
6. Если новый Git-ответ начинается позже дня, следующего за `data_through`,
   потерянные даты записать в `unobserved_ranges`. Их нельзя восстановить
   предположением или разницей скользящих итогов. Дальнейшие известные дни
   можно сохранить, но итог пометить как неполный в пояснении и отчёте.
   Аналогично поступить с отсутствующими датами внутри любого ответа.
7. Если нужно освежить справочное число архивов, прочитать **все страницы**
   GitHub releases и просуммировать `download_count` прикреплённых `.zip`/`.tgz`.
   Контрольные суммы и автоматически создаваемые исходные архивы не включать.
   Это уже накопительные счётчики файлов: заменить снимок, не прибавлять его
   целиком к прежнему значению. При удалении или пересоздании файла отметить
   нарушение сопоставимости вместо догадки о пожизненном итоге.
8. Сохранить дневные записи, итоги, реальные границы данных и новую дату проверки
   в реестре. Добавить запись в `updates`: старые и новые итоги, новые даты,
   прирост за новые дни, исправления пересекающихся дней и обнаруженные пробелы.
   Разница итогов = новые дни + исправления старых дней.
9. Обновить число, `aria-label` и `<title>` в
   [npm SVG](assets/badge-npm-downloads.svg) и [Git SVG](assets/badge-clones.svg).
   Обновить alt-тексты, пояснение и диапазон ссылки npm в [README](../README.md).
   В этом документе обновлять таблицу текущего снимка; исходная запись остаётся
   в журнале реестра. Проверить SVG и `git diff --check`, затем сообщить
   пользователю прежние и новые значения, прирост и фактическую дату данных.

При ошибке запроса сохранить последний успешный результат и его дату, сообщить
об ошибке. Не обнулять счётчик и не выдавать старое значение за свежее.
Эта процедура сама по себе не разрешает commit, push, публикацию или добавление
сбора телеметрии; соблюдать авторизацию текущей задачи.

## Пример обновления через четыре дня

Если следующая проверка будет 7 ноября и источники уже отдадут данные по 5 ноября,
к исходному снимку добавятся **2, 3, 4 и 5 ноября**. Повторно полученные дни
октября и 1 ноября используются для сверки и второй раз не прибавляются.
Это пример, не обещание конкретной задержки источников: использовать реальные
границы ответов. Начинать с 4 ноября только потому, что предыдущая проверка
прошла 3 ноября, было бы ошибкой — потерялись бы запаздывавшие 2 и 3 ноября.

Обновление через 3–4 дня подходит для сохранения Git-истории. Если интервал
приблизится к 14 дням или превысит его, часть данных может стать недоступной.
Автоматическое расписание и фоновый сбор **не настроены**: обновление выполняется
по просьбе пользователя. Даже при дальнейших обновлениях Git-история начинается
с 19 октября 2026 года, а не с создания репозитория.
